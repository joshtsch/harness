# Issue tracker: GitHub

Issues and specs for this repo live as GitHub issues. Use the `gh` CLI for all operations.

## Conventions

- **Create an issue**: `gh issue create --label needs-triage --title "..." --body "..."`. The `needs-triage` label is mandatory intake state.
- **Read an issue**: `gh issue view <number> --comments`
- **List issues**: `gh issue list --state open --json number,title,body,labels,comments`
- **Comment on an issue**: `gh issue comment <number> --body "..."`
- **Apply / remove labels**: `gh issue edit <number> --add-label "..."` / `--remove-label "..."`
- **Close**: `gh issue close <number> --comment "..."`

Run `pnpm check:triage` before treating open issues as ready. It queries open
issues and fails when a ready issue lacks exactly one issue-type label
(`bug`/`enhancement`), when readiness conflicts with `needs-triage`, or when an
issue has neither intake nor a complete ready state.

Session setup resolves every implementation session through the configured issue
tracker. GitHub sessions require a numeric issue number and use `gh issue view`
against the configured repository; missing issues, unavailable access,
unsupported trackers, and malformed responses fail before cloning or worktree
creation. There is no exploratory implementation bypass.

For session setup, use the repository configured under the selected project's
issue tracker. Other repository-scoped `gh` commands may infer their repository
from `git remote -v` when run inside this clone.

## Triage comment requirement

AI-generated issue summaries, specifications, or acceptance criteria must begin
with this exact disclaimer:

> *This was generated by AI during triage.*

Keep the disclaimer in the issue body when editing or refining AI-generated
triage content. Do not add secrets, credentials, raw MCP output, or PII to issue
bodies or comments.

## Pull requests are for change requests

Handle pull requests as change requests, not as incoming feature requests for triage.

When a skill says to publish to the issue tracker, create a GitHub issue. When it says to fetch the relevant ticket, run `gh issue view <number> --comments`.

## Markdown publication gate

Review the exact markdown payload before sending it to GitHub or another external consumer. Save it to a temporary file and run `pnpm check:markdown -- path/to/payload.md`, or pipe generated content with `pnpm check:markdown -- --stdin`. Stop on any finding, correct the source, and rerun the check before `gh issue create`, `gh issue edit`, `gh issue comment`, or change-request publication. This check covers malformed headings, list markers, links, images, and unclosed fenced code blocks; it does not replace human review of meaning, links, or sensitive content.
